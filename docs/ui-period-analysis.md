# 기간 기능 3중 구조와 UI 배치 분석 (2026-08-06)

2026-08 초에 기간 관련 기능이 한꺼번에 늘었다(최근 N년 프리셋, 탭별 시즌/버전
나눠보기, 기간별 탭 버전 단위, 상대전적 기간설정, 리포트 버전 범위). 그 결과
**"기간으로 자르는 곳"이 세 겹**이 됐고, 사용자가 "ID 검색 하부에 이 부분이
있는데 실제로 하위 항목에서 데이터를 또 기간별로 나누고 있어"라고 지적했다.
이 문서는 그 시점의 전체 구조를 지도로 그리고, 발견된 문제를 우선순위로 적는다.

## 1. 기간 기능이 사는 세 곳 (지도)

| 층 | 위치 | 동작 방식 | 무엇을 자르나 |
|---|---|---|---|
| ① 조회 기간 (상단) | 검색 폼 아래 | **서버 재조회** — 모든 탭이 다시 계산됨 | 화면 전체 |
| ② 탭 안 나눠보기 | 캐릭터·강점·약점·스테이지·상대캐릭·레이팅대·라운드(시즌/버전), 시즌 탭(버전별), 기간별 탭(집계 단위), 상대전적(만난 시기+기간설정) | **클라이언트 전환** — 이미 받은 표를 갈아끼움 | 그 탭 하나 |
| ③ 리포트 범위 바 | /player/id/report | **링크 이동** — 서버 렌더 재실행 | 리포트 전체 |

세 층은 실제로는 역할이 다르다: ①은 "이 기간의 나"를 다시 계산하는 필터,
②는 "전체 기간 안에서 구간별 비교"를 보는 렌즈, ③은 공유용 스냅샷 범위.
**기능 중복이 아니라 역할 분담이 맞다** — 문제는 화면이 그 역할 차이를
설명하지 않아서 같은 것이 세 번 있는 것처럼 보인다는 데 있다.

> **후속 결정 (2026-08-06, 사용자):** 설명으로 풀지 않고 **① 층을 통째로
> 제거**하기로 했다. 조회는 항상 전체 이력이고, 기간을 좁히는 일은 ②(탭 안)로
> 일원화. 근거: 서버는 어차피 항상 전체를 받아 캐시 위에서 자르고 있었으므로
> ①은 "재조회 비용을 내고 같은 데이터를 다시 자르는" 층이었다. 이로써 P4(버튼
> 인플레이션)는 자연 해소, P2 도 남은 '기간설정'이 상대전적 한 곳뿐이라 원래
> 라벨 충돌이 사라졌다(그래도 '날짜로 지정' 이름은 유지). 옛 공유 링크의
> pm= 파라미터는 조용히 무시되고 전체 조회로 열린다 — 필터된 상태로 열어주면
> 그걸 풀 버튼이 화면에 없기 때문. 서버 API 의 start/end/season 파라미터는
> 리포트 페이지·외부 사용자를 위해 그대로 남겼다.

## 2. 발견된 문제 (우선순위순)

### P1 — 구성 % 분모 불일치 (실제 버그)

탭 안 나눠보기의 "8,154판 · 전체의 50.8%" 힌트:
- 분자 `effSplitSpan.games` — **전체 이력** 기준(`seasons`/`versions`, 서버가
  전체 레코드에서 계산)
- 분모 `single.recordCount` — **① 조회 기간 필터 적용 후** 값

①에서 기간을 좁히면(예: 기간설정으로 S1의 절반만) 분자가 분모보다 커져
**100%를 넘는 %가 표시될 수 있다.** 기간 표시(start~end)도 전체 이력 기준이라
표 내용(필터된 절반)과 어긋난다.

고치는 방향 두 가지, 하나만 고를 것:
- (a) 분모를 `totalCount`(전체 이력)로 바꾸고 문구를 "전체 이력의 N%"로 — 값은
  항상 일관되지만, ①로 좁힌 상태에선 표와 힌트가 다른 모집단을 말하게 된다.
- (b) 서버가 **필터 적용 후** 레코드로 spans 를 한 벌 더 계산해 내려보낸다 —
  표와 힌트가 항상 같은 모집단. 응답 몇 줄 늘어나는 비용뿐. **이쪽 권장.**

### P2 — 같은 이름 "기간설정" 두 개 동시 노출

상대전적 탭을 열면 화면에 "기간설정" 버튼이 두 개다(① 조회 기간 + 상대전적
'만난 시기'). 뜻도 다르다 — 전자는 "경기가 벌어진 기간", 후자는 "그 상대를
**마지막으로 만난** 날". 라벨을 갈라야 한다. 예: 상대전적 쪽을 "직접입력"으로
되돌리거나 "날짜로 지정"으로.

### P3 — 시즌 버튼 순서가 조회 후 뒤집힘

- 조회 전: `FALLBACK_SEASONS = ['S1','S2','S3']` → S1 S2 S3
- 조회 후: `seasonSpans()`가 최신 우선 정렬 → S3 S2 S1

첫 조회 순간 버튼 순서가 뒤집힌다. 한쪽으로 통일할 것 — 탭 안 나눠보기
하위 버튼(S1→S3 오름차순)과 맞추려면 **오름차순으로 통일**이 자연스럽다
(fallback 을 그대로 두고 seasonSpans 결과만 뒤집으면 된다. 단, 리포트 범위
바도 같은 spans 를 쓰므로 함께 확인).

### P4 — ① 조회 기간 줄의 버튼 인플레이션

현재 10개(전체/월별/연별/최근2·3·4년/기간설정/S1/S2/S3), 시즌이 열릴 때마다
+1. 그리고 **최근 2/3/4년은 지금(게임 수명 2.4년) 셋 다 사실상 '전체'와 같다**
— 자리 셋을 차지하면서 당장은 변별력이 없다. 제안:
- 최근 N년 셋을 버튼 하나("최근 N년 ▾" 셀렉트)로 접거나,
- 아예 기간설정 안의 프리셋으로 넣는다(리포트 범위 바의 최근 30일/90일/올해와
  같은 패턴).
시즌 버튼도 S5·S6 이 열리면 같은 문제가 온다 — 최신 2~3개 + "이전 시즌 ▾".

### P5 — '전체'라는 라벨의 남발

한 화면에 '전체'가 최대 6곳(조회 기간·캐릭터 칩·무작위 지역·최소 경기·만난
시기·나눠보기·보여줄 수). 각 버튼 그룹 앞에 라벨(ctl-label)이 있는 곳(최소
경기·만난 시기·보여줄 수)과 없는 곳(나눠보기, 캐릭터/표 전환 등)이 섞여 있다.
**모든 버튼 그룹에 라벨을 붙이는 것**이 지난 피드백("상위·하위 버튼 경계가 안
보인다")의 일반해다 — split-sub 의 들여쓰기+왼쪽 경계선 패턴을 다른 하위
그룹에도 확장.

### P6 — 첫 화면에서 데이터까지의 스크롤 거리

조회 직후 화면 순서: 폼 → 랭크 배지 → 오늘 요약 → 멘트 → **캐릭터 칩 41개**
→ 무작위 패널 → 리포트/다운로드 버튼 → 탭 줄 → 표. 캐릭터 칩이 41개 전부
펼쳐져 있어(랭크 배지는 "더 보기"로 접는데 칩은 안 접음) 실제 데이터까지
3~4스크롤이 필요하다. 칩도 상위 N개 + "더 보기"로 접는 것을 권장.
무작위 패널도 조회 **결과가 떠 있는 동안**은 접거나 결과 아래로 내리는 것을
검토할 만하다 — 조회 전에는 발견 경로로 필요하지만, 결과를 보는 중에는
폼과 표 사이에 끼어 있는 무관한 상자다.

### P7 — 응답 크기 감시 항목 (아직 문제 아님)

나눠보기 표 6종×2(시즌/버전)가 응답에 추가됐다. 행 수는 캐릭터(≤42) ×
버전(실측 28) 곱까지 갈 수 있다 — 라운드(17열) 버전별이 최대 ~950행 × 17열.
지금은 수십 KB 수준이라 괜찮지만, **"경기 수에 비례하지 않는다"는 기존
원칙과 달리 이 표들은 버전 수에 비례**하므로 시즌이 쌓이면 다시 잴 것.
필요해지면 버전별 표만 지연 로드(탭에서 요청 시)로 바꾸는 게 자연스러운 지점.

### P8 — 모바일에서 버전 버튼 28개

버전별 나눠보기 하위 버튼이 28개(3줄 이상 wrap)다. 데스크톱은 견딜 만하지만
모바일에서는 화면 반을 차지한다. 개수가 임계(예: 12개)를 넘으면 버튼 대신
`<select>` 로 떨어뜨리는 분기를 권장(이미 sp-select 스타일이 있다).

## 3. 잘 되어 있는 것 (유지)

- ①·②·③의 **역할 분담 자체는 옳다** — 합치면 오히려 "전체 대비 구간 비교"가
  불가능해진다. 필요한 건 통합이 아니라 라벨링이다.
- 데이터가 받쳐줄 때만 버튼이 생기는 규칙(granOptions·h2hMinOptions·
  hasMultiSeason)이 전 기능에 일관되게 적용돼 있다.
- 나눠보기의 기간·구성·표본 경고 힌트는 방향이 맞다 — P1 만 고치면 된다.
- 시즌 경계를 데이터(game_version)에서 파생하는 원칙이 모든 신기능에 유지됐다.
