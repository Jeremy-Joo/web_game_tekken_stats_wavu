# 레이팅 구간대별 랭크업 손익분기 승률 실측 (2026-08-07)

"하위~중위권은 승률 50% 이하여도 랭크가 오르고, 상위권(81~100%)은 55%+ 또는
95%+가 필요하다"는 감각을 실측으로 확인했다. 관련 문서: [rank-point-attempt.md](rank-point-attempt.md)
(반다이남코 랭크 포인트 자체를 복원하려다 실패한 시도), [tekken8-rating-gain-loss-research.md](tekken8-rating-gain-loss-research.md)
(승/패 점수 비대칭의 공식 근거).

## 결론 먼저

| 레이팅 구간 | 손익분기 승률 |
|---|---|
| 750~1749 | **없음 — 측정된 모든 승률 구간(0~9%부터)에서 평균 단 변화가 항상 양수.** 승률이 손익분기를 정하는 게 아니라 이 구간 자체가 구조적으로 우호적이다. |
| 1750~2749 | 대략 **50% 근방** (±0.1 안쪽에서 부호가 바뀐다) |
| 2750~2999 (실측 최상위) | **60~65%**는 돼야 손익분기 |
| 0~749, 2999+ | 표본 부족(인구 자체가 적음)으로 판단 보류 |

원래 감각("81~100%는 55%+ 또는 95%+")보다 실제 그림이 더 극적이다 — 저단은
그냥 "낮아도 되는" 정도가 아니라 **승률과 거의 무관하게 오르는 구조**였고,
[tekken8-rating-gain-loss-research.md](tekken8-rating-gain-loss-research.md)가
인용한 공식 사양("옐로 랭크는 패배해도 점수를 잃지 않는다")과 정확히 들어맞는다.
반대로 압박이 걸리는 지점은 감각보다 좁다 — 1750부터 시작해서 2750에서 한 번 더
뛴다.

## 1. 왜 rank-point-attempt.md 와 다른 문제인가

rank-point-attempt.md 는 반다이남코의 **숨겨진 점수 공식 자체**(1경기당 몇 점)를
복원하려다, 검증 수단이 자기 자신뿐이라는 문제로 되돌렸다. 이번 조사는 그 공식을
복원하지 않는다 — wavu 가 경기마다 그대로 주는 `myRank`(단, 0~37 정수)가 **실제로
올랐는지만 직접 센다.** 숨은 변수를 추정할 필요가 없어 rank-point-attempt.md 의
핵심 실패 원인(자기검증)이 애초에 발생하지 않는다.

## 2. 방법론

1. **정찰** — 관리자 화면에서 내려받은 28일 GA 조회 기록(admin export)으로 레이팅
   구간(250 단위)별 표본이 이미 몇 명 있는지 확인.
2. **보강** — admin export 는 "이 사이트를 검색한 사람"이라 편향이 있다
   (`lib/tekken/player-index.ts` 머리말 참조). 부족한 구간만 wavu 실시간 피드로
   편향 없이 채운다.
3. **수집·분석** — 최종 후보자(구간당 최대 40명)의 전체 경기 이력을 **캐릭터별로
   나눠**(단은 캐릭터마다 따로 관리된다 — rank-point-attempt.md 경고) 30판
   슬라이딩 윈도우로 잘라, 윈도우별 승률과 단 변화(끝단 − 시작단)를 기록.
4. **집계** — 승률을 10%p 단위로 나눠 구간×승률버킷별 평균 단 변화를 그대로 센다.
   **회귀·곡선적합을 쓰지 않았다** — rank-point-attempt.md 가 자기검증으로 신뢰를
   잃은 전례가 있어, 관측치를 그대로 보여주는 쪽이 더 정직하다.

스크립트: `scripts/build-rank-threshold-data.ts`. 이어하기(JSONL 체크포인트)
지원, wavu 요청은 순차(예의 1.2초 간격).

## 3. 헤비 유저 편중 — 실측하고 바로잡았다

1차 집계에서 윈도우가 14만 개나 나와 이상해서 확인해보니, **상위 11%(451명 중
50명)가 전체 윈도우의 40.3%**를 차지하고 있었다(1등 한 명이 4,634개, 전체의
3.3%). 몇만 판을 친 헤비 유저 한 명이 자기 커리어 내내 지나온 여러 구간에서
수백~수천 개 윈도우를 혼자 만들어낸 것 — 이 윈도우들은 서로 독립이 아니라
"같은 사람의 반복된 습관"이라, n이 커 보여도 실제 신뢰도는 훨씬 낮았다.

**(플레이어, 구간) 조합마다 최대 5개 윈도우로 캡**을 걸어 재집계했다(균등 간격
표본 — 특정 시기에 쏠리지 않게). 캡 적용 후 저단(750~1749)에서 나타났던 일부
음수 구간이 사라지고 전부 양수로 정리됐다 — 헤비 유저 몇 명의 저조한 시기가
평균을 오염시키고 있었다는 뜻이다.

## 4. 동시 실행 사고

집계 도중 같은 스크립트가 두 곳(터미널 + 별도 실행)에서 동시에 돌아, 25명이
중복 처리되고 윈도우 1,063개가 중복 기록됐다. 처리 순서상 먼저 기록된 패스만
남기고 나중 중복분을 제거한 뒤 재집계했다 — **최종 결과 표는 이 정제를 거친
값**이다. wavu 순차 요청 원칙이 이런 사고로 깨질 수 있다는 실례라, 스크립트를
여러 곳에서 동시에 돌리지 말 것.

## 6. 캐비엇 — 이 결과를 쓸 때 주의할 것

- **표본이 "이 사이트를 쓰는 사람"에 뿌리를 두고 있다.** admin export 로 채운
  구간(1000~2249)은 wavu 피드 보강 없이 그대로 썼다 — 사이트 방문자 편향이
  완전히 제거되진 않았다. 편향이 실제로 결과를 얼마나 바꾸는지는 검증 안 됨.
- **저단(0~749)·최상위(3000+)는 표본이 원래 얇다.** 인구 자체가 적어(0~749는
  admin export 에 2명뿐) 결론을 못 낸다 — wavu 를 더 돌려도 근본적으로
  한계가 있다(rank-point-attempt.md 도 같은 문제를 지적했다).
- **캐릭터를 안 가리고 합쳤다.** 한 사람이 여러 캐릭터를 치면 캐릭터별로 따로
  집계되지만, 캐릭터 간 숙련도 차이는 반영 안 됨.
- **30판 윈도우 크기는 임의값이다.** 더 짧게/길게 자르면 숫자가 달라질 수 있다 —
  민감도 분석은 안 했다.
