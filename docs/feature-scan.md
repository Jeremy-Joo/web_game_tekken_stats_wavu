# 다른 분석 사이트 대조 — 무엇을 가져오고 무엇을 안 가져오는가

같은 형식의 사이트들을 훑어 **이 사이트에 없는 기능**과 **일부러 안 만들 기능**을 갈랐다.
결론은 둘이다: 참고할 곳은 전적 트래커가 아니라 **개인 분석 사이트**고,
당장 넣을 만한 건 이미 있는 데이터를 다르게 배치하는 것뿐이다.

상태: **정리 완료** (2026-08-04 · 배포됨)

| 항목 | 결과 |
|---|---|
| ② 시즌 경계선 | **적용** — 메인 추이 차트 + 리포트 |
| ① 활동 히트맵 | **적용** — 일별 탭 `달력` 보기 + 리포트 `날짜별 활동` |
| 내 계정 고정 | **적용** — 5장 참조 |
| 레이팅대 리포트 노출 | **이미 있었다** — `secGap` 절. 후보 목록이 낡았던 것 |
| 퍼센타일 배지 | **만들었다가 뺐다** — 5장 참조 |
| 글리프(육각형) | **폐기** — 코드·연구 데이터만 보관. 4-E 가 그 기록 |

> 조사 뒤 **글리프(6축 백분위)가 다른 작업에서 먼저 들어왔다**(`lib/tekken/hexagon.ts`).
> 셋을 한 사람 데이터로 합쳐보니 **서로가 서로의 근거가 되는 게 확인됐다** — 4-C 참조.
> 이게 이 문서의 결론을 바꿨다: 셋은 별개 기능이 아니라 **한 묶음**이다.

## 1. 포지션

> **2026-08-04 전면 수정.** 이 장은 원래 "ewgf 는 인구, 여기는 개인 — **경쟁 아님**"
> 이었다. **틀렸다.** 아래 1-A 가 그 정정이고, 1-B 가 다시 조사한 지형이다.

### 1-A. 정정 둘

**① ewgf 는 개인 페이지도 갖고 있다.** 아카이브된 프론트엔드 저장소
([ewgf-gg/ewgfgg-frontend](https://github.com/ewgf-gg/)) 의 컴포넌트 이름에 그대로 남아 있다 —
`BestMatchupChart` · `WorstMatchupChart` · `WinrateOverTimeChart` · `TekkenPowerChart` ·
`RecentBattlesCard` · `StatPentagonChart`. `/player/<식별코드>` 라우트도 있다.
**여기가 하는 일과 겹친다.** "인구 대 개인"으로 갈라뒀던 전제가 성립하지 않는다.
겹치지 않는 건 okizeme·tekkendocs 같은 프레임 데이터 쪽뿐이다.

- `StatPentagonChart` 는 5축 방사형이다. 우리가 4-E 에서 폐기한 육각형과 같은 물건이고,
  ewgf 는 전수 데이터가 있으니 백분위로 그려도 4-E 의 문제 ①②가 안 생긴다.
  **폐기 판단은 유지한다** — 그 데이터를 신뢰성 있게 유지할 방법이 여기엔 없다는 게 이유였다.

**② ewgf 링크는 없다.** 원래 "철권 티어 링크로 ewgf 쪽을 연결해뒀다"고 적혀 있었다.
`app/page.tsx` 의 `철권 티어`·`잡기 풀기` 는 둘 다 `season-end-web.vercel.app`
(같은 사람의 다른 사이트)로 간다. 저장소 전체에 ewgf 로 나가는 링크는 하나도 없다.

### 1-B. 지형 (2026-08-04 조사)

**전부 같은 우물을 판다.** wank.wavu.wiki 가 공식 리플레이 API 를 60초마다 긁고,
나머지가 그걸 받아 쓴다. ewgf 백엔드 README 가 출처를 "공식 서버와 Wavu Wank API"
라고 직접 밝힌다. 즉 **데이터 접근성은 차별점이 아니다.**

| 사이트 | 성격 | 개인 페이지 | 상태 |
|---|---|---|---|
| [wank.wavu.wiki](https://wank.wavu.wiki/) | 상류. glicko2 레이팅·지역 리더보드·매치업 | 있다 (`/matchups`) | 살아 있음. 605M 경기 |
| [ewgf.gg](https://ewgf.gg/) | 인구 + 개인 양쪽 | 있다 | 살아 있으나 **2025-10/11 저장소 아카이브 후 비공개 전환** |
| [tknow.gg](https://tknow.gg/) | 리더보드·실시간 접속·대회 일정·통계 | 있다 | 살아 있음. KR/EN/JP · **안드로이드 앱** |
| kekken.com | 랭크대별 캐릭터 승률·개인 프로필 | 있었다 | **죽었다** (도메인 파킹) |
| tekkenstats.gg | 개인 전적 | 있었다 | **죽었다** (DNS 소멸, 서버비가 원인이라는 정황) |

**둘이 죽었다.** 그리고 둘 다 DB 를 이고 있었다 — kekken 은 "몇 주 묵은 데이터"가
불평의 대상이었다. 여기는 **DB 가 없다.** 요청마다 받아서 그 자리에서 집계하고 10분 캐시한다.
이건 원래 레이트리밋 대응이었는데, 결과적으로 **묵을 수가 없고 유지비가 안 든다.**
5장에서 다룬 어떤 기능보다 이게 크다.

**tknow 에 스테이지별 통계가 있다.** `/stats` 에 `Stages` 탭이 있다.
CLAUDE.md 는 "스테이지 이름 매핑이 없어 만들지 말 것"으로 막아뒀는데,
**저쪽이 갖고 있다면 매핑을 구할 길이 있다는 뜻이다.**
금지를 풀자는 게 아니라, 막아둔 이유("알 방법이 없다")가 더는 확실하지 않다는 기록이다.

## 2. 철학이 가장 가까운 곳 — 트래커가 아니라 개인 분석 사이트

[op.gg](https://op.gg/) · [tracker.gg](https://tracker.gg/) 같은 대형 트래커는 **숫자를 보여주고 끝난다.**
이 사이트는 숫자에 해석과 성격을 붙인다. 그래서 참고 대상이 다르다.

- **[Lichess Insights](https://lichess.org/insights)** — 사상이 제일 비슷하다. 무료, 개인 데이터 전체를
  받아서 여러 축(오프닝·시간대·상대 유형)으로 잘라 보여준다. 탭 구조가 이미 이 모양이다.
- **[AoE4 World](https://aoe4world.com/)** — 소규모 팀의 개인 전적 사이트라 규모감이 비슷하다.
  거기서 가져올 것: **레이팅 그래프에 패치/시즌 경계선을 세로선으로 긋는다.**

## 4. 당장 넣을 것 둘 — 새 계산이 없다

둘 다 **이미 있는 데이터를 다르게 배치**하는 것뿐이다.
모의 화면을 실데이터(JackFather 909경기)로 만들어 확인했다.

### ① 활동 히트맵 (GitHub 잔디)

`buildDaily()` 가 만드는 숫자를 달력 격자로 옮긴다. 변환 로직 없음.

**배치만 바꿨는데 표에서 안 보이던 성격이 나왔다** — 실측:

| | 값 |
|---|---|
| 최근 1년 플레이한 날 | **19일** |
| 하루 최다 | **91판** |
| 최장 공백 | **173일** |

1년에 19일만 접속하는데 접속하면 하루 91판을 치고 반년 가까이 손을 놓는다.
**"몰아서 하는 유형"** 이라는 게 한눈에 보인다. 33행짜리 표를 다 읽어도 이건 안 잡힌다.

리포트 페이지 상단에 넣으면 "이 사람은 어떤 사람인가"를 문장 없이 보여준다.

**정하고 들어가야 할 것 — 색 단계 기준.**
모의 화면은 최댓값 기준 상대값으로 잡았는데(91판 = 최고 진하기),
이러면 **몰아서 하는 사람은 대부분 칸이 연해 보인다.**
절대 기준(예: 10 / 25 / 50판)으로 자르는 편이 나을 수 있다.
실제 유저 분포를 봐야 정할 수 있으므로 넣을 때 결정한다.

### ② 레이팅 추이에 시즌 경계선

지금 추이 그래프는 선 하나뿐이고 가로축이 2년이 넘는데 구간 표시가 없어
**"언제부터 달라졌나"를 눈으로 못 짚는다.** 세로 점선 3개만 그으면 된다.

**핵심은 경계 날짜를 코드에 안 적는 것이다.** `seasons.ts` 가 `game_version` 에서
파생시키므로 S4 가 열려도 저절로 따라간다 — CLAUDE.md 의
"시즌 경계 날짜를 코드에 다시 적지 말 것"을 그대로 지키는 형태다.

실측으로 읽히는 것: S1 종료 후 오래 쉬었다가 S2 에 복귀, S3 에서 경기 수 최다(468판).

## 4-C. 셋을 합쳐야 문장이 나온다 (2026-08-04 확인)

글리프·히트맵·시즌선을 **한 사람(JackFather 909경기)** 데이터로 나란히 놓고 확인했다.
따로 보면 각각 그림 하나지만, 붙이면 **한 성질을 세 방향에서 같이 가리킨다.**

| 그림 | 값 | 말하는 것 |
|---|---|---|
| 글리프 | 지구력 **0.90배** (본전 1.0 아래) | 세션 후반 승률이 초반의 90% |
| 히트맵 | 하루 최다 **91판** · 전체 842일 중 **32일**만 접속 | 접속하면 몰아서 친다 |
| 흐름 탭 (기존) | **21판째부터 −7.6%p** | 딱 그 지점에서 꺾인다 |

→ **"몰아서 오래 치는데 정작 길게 하면 무너지는 사람"**

우연이 아니라 구조적이다. 글리프의 `몰입`(하루 28.4판)과 `지구력`(0.90배)이
같은 사람에게서 반대로 나오는 것이 히트맵 모양과 정확히 대응한다.

> **2026-08-04 정정** — 처음 이 표를 쓸 때는 글리프 값이 **백분위**(모집단 80명 대비)였다.
> 백분위는 폐기했다(4-E 참조). 위 값은 절대 눈금 기준으로 다시 적은 것이다.
> `1년에 19일`도 최근 1년 기준이라 전체 기간(842일 중 32일)으로 고쳤다.

**그래서 배치 결론이 바뀐다.** 셋을 서로 다른 탭에 흩어 놓으면 이 연결이 안 보인다.
**리포트 페이지 한 화면에 같이 올려야 한다** — 리포트가 "이 사람은 이런 플레이어다"를
한 흐름으로 재배치하는 페이지라는 원래 목적과도 맞는다.

### 글리프 쪽에 하나 — 원값을 같이 내야 한다

`HexScore` 가 `raw`(원래 값)를 눈금 위치와 **같이** 들고 있는 게 이 설계의 핵심이다.
화면에도 같이 나와야 한다. 위치만 띄우면 무엇을 잰 건지 감춰지고,
`app/jokes.ts` 가 세운 "근거 없이 말하지 않는다" 원칙과 어긋난다.

### 남은 논점 — 축 이름 `역상성`

6축 중 이 하나만 라벨로 뜻이 안 온다(나머지 다섯은 읽힌다).
설명을 봐야 이해되는 축은 아이콘 크기(52px, 라벨 없음)에서 특히 불리하다.

## 4-D. 히트맵 색 기준 — **절대 기준으로 정했다**

> 결론: `1 / 10 / 25 / 50경기` 를 경계로 하는 절대 기준으로 넣었다.
> 아래는 그 판단 과정이다.

합본에서 드러난 미결이었다. 색 4단계를 **최댓값 기준 상대값**으로 잡았더니
하루 91판이 최고 진하기가 되어 **나머지 칸이 전부 연해 보인다.**
몰아서 하는 사람일수록 자기 그림이 밋밋해지는 역설이 생긴다.

| 안 | 장점 | 단점 |
|---|---|---|
| 상대 (지금) | 사람마다 대비가 살아난다 | **사람 간 비교가 안 된다.** 91판과 12판이 같은 색일 수 있다 |
| 절대 (10 / 25 / 50판) | 색이 곧 판수 — 비교 가능 | 라이트 유저는 전부 최하 단계로 깔린다 |

실제 유저 분포를 봐야 정할 수 있다. **절대 기준 쪽이 유력하다** —
이 사이트는 여러 명 비교가 기본 기능이라, 같은 색이 같은 뜻이어야 한다.

## 4-E. 글리프에서 백분위를 걷어냈다 — **연구 기록** (폐기)

> **이 축은 제품에 넣지 않기로 했다.** 아래는 왜 백분위가 틀린 방식이었는지에 대한
> 기록이고, 결론(점수는 조회자 데이터와 고정 상수만으로 내야 한다)은 다른 지표를
> 만들 때도 그대로 유효하다. 코드는 `lib/tekken/hexagon.ts` 에 남아 있지만
> `app/` 어디서도 import 하지 않는다.

**점수를 남의 전적과 비교해 내면 안 된다.** 조회자의 데이터와 고정 상수만으로 정해져야 한다.

### 왜

| | 문제 |
|---|---|
| 1 | **조회자가 한 판도 안 쳤는데 모양이 바뀐다.** 모집단을 80명→300명으로 다시 뽑으면 같은 사람의 실력이 91.8에서 달라진다. `app/jokes.ts` 의 "조회 결과가 같은데 말이 달라지면 신뢰가 깎인다"와 정면으로 어긋난다 |
| 2 | **시즌마다 낡는다.** 레이팅 분포가 통째로 움직여 기준값을 다시 만들어야 하고, 안 만들면 조용히 틀린 값이 나간다. `seasons.ts` 에서 "시즌 경계 날짜를 코드에 적지 말 것"이라고 정한 것과 반대 방향 |
| 3 | **피하기로 한 의존성을 뒷문으로 들여온다.** 인구는 ewgf, 개인은 여기 — wavu 레이트리밋 때문에 인구 데이터는 신뢰성 있게 유지할 수도 없다 |
| 4 | **표본이 무작위가 아니었다.** wavu 공개 피드에서 500판 이상만 뽑아 헤비 유저에 치우쳐 있다 |

### 어떻게 — 축마다 고정 눈금

`hexScores(records)` 로 인자를 하나만 받게 바꿨다. 남의 전적이 들어올 자리가 없다.

| 축 | 눈금 | 기준선 | 근거 종류 |
|---|---|---|---|
| 실력 | 35% ~ 65% | 50% | **확률** — best-of-5에서 경기 승률 23.5%~76.5% 지점 |
| 다양성 | 0 ~ 1 | 없음 | **정의** — 정규화 엔트로피 그 자체 |
| 몰입 | 0 ~ 60판 | 없음 | **기존 상수** — `advice.ts` 의 `MAX_POS=60`(분석 한계) |
| 상승세 | −400 ~ +400 | 0 | **레이팅 시스템** — Elo 한 등급(기대승률 10:1) |
| 지구력 | 0.6 ~ 1.4배 | 1.0 | **정의** — 1.0=초반과 같음. 폭 ±0.4는 관례 |
| 역상성 | 0% ~ 60% | **42.9%** | **Elo 기대승률** `1/(1+10^(50/400))` |

기준선(`neutral`)은 **지표 정의에서 나오는 것만** 넣는다. 기준선은 "여기가 본전"이라는
단언이라 근거 없이 그리면 거짓말이 된다. 다양성·몰입은 본전이랄 게 없어 `null` 이다.

### 값이 이렇게 바뀐다 (JackFather 909경기)

| 축 | 원값 | 백분위(폐기) | 절대 눈금 | 기준선 대비 |
|---|---|---|---|---|
| 실력 | 55.2% | 91.8 | **67.4** | 50 위 ▲ |
| 다양성 | 0.58 | 52.9 | **58.4** | — |
| 몰입 | 28.4판 | 74.6 | **47.3** | — |
| 상승세 | −35 | 24.1 | **45.6** | 50 아래 ▼ |
| 지구력 | 0.90배 | 4.9 | **38.0** | 50 아래 ▼ |
| 역상성 | 21.5% | 33.1 | **35.8** | 71 아래 ▼▼ |

**역상성에서 백분위가 감추고 있던 게 드러났다.** 백분위 33.1은 "중하" 정도로 읽히는데,
절대 눈금으로는 Elo가 예측하는 42.9%에 한참 못 미치는 21.5%다.
남들도 못 하니까 33등급이었을 뿐, **레이팅 시스템 기준으로는 확실히 기대 이하**다.

### 대가 — 모양의 대비가 줄었다

원래 헤더가 경고한 그대로다: *"원값을 그대로 얹으면 전부 같은 모양이 된다."*

| | 값의 폭 |
|---|---|
| 백분위 | 4.9 ~ 91.8 (**86.9**) |
| 절대 눈금 | 35.8 ~ 67.4 (**31.6**) |

막대 길이만으로는 사람이 잘 안 갈린다. **대신 기준선이 의미를 진다** —
"50보다 위인가 아래인가"가 읽는 축이 된다.
아이콘 크기(52px·라벨 없음)에서 이게 성립하는지는 **아직 확인 못 했다.**
성립 안 하면 눈금 폭을 좁히는 게 답이지, 백분위로 되돌아가는 건 답이 아니다.

### 지키는 장치

`scripts/check-hexagon.ts` (`npm run check` 에 연결, 28건). 검사하는 것:

- `hexScores` 인자가 하나뿐인가 + **본문에 `baseline`/`percentile` 문자열이 없는가**(소스를 읽어서 확인)
- 기준선이 지표 정의값과 일치하는가 (실력 0.5 · 상승세 0 · 지구력 1.0 · 역상성 Elo값)
- 눈금 밖 값이 0~100을 안 넘는가
- 표본 부족 축이 `null` 인가 (0으로 안 채우는가)

이 검사가 만들자마자 **내 산수 오류를 잡았다** — Elo 기대값을 0.42864로 적었는데
실제는 0.428537이다.

## 5. 후보 셋 — 결과

세 항목의 결말이 다 달랐다. 그 차이가 이 문서에서 제일 남길 만한 부분이다.

### 레이팅대별 분해 — **이미 있었다**

후보로 적어뒀는데 리포트에 `secGap` 절이 이미 있었다(`상위 상대 37.9% · 동급 49.2% ·
하위 71.5%`). **목록이 낡은 것을 못 알아채고 구현하려 했다.**
→ 후보를 적을 때는 그 시점에 없다는 것까지 확인해야 한다.

### 내 계정 고정 — **적용**

최근 조회 목록은 있었지만 매번 다시 눌러야 했다. 고정하면 다음 방문에 자동 조회된다
(브라우저에만 저장). `?id=` 로 들어온 공유 링크가 우선이다 — 남이 보낸 링크를
내 계정으로 덮으면 안 된다.

**배치를 한 번 되돌렸다.** 처음엔 최근 조회 칩마다 별(☆/★)을 달았는데,
`app/i18n.ts` 머리 주석이 *"아이콘은 두지 않는다 — 버튼이 여럿 붙어 있는 줄에서
시선이 분산되고 줄바꿈을 예측할 수 없다"* 고 정해둔 상황과 정확히 같았다.
지금은 고정된 하나만 줄로 밝히고(`내 계정: JackFather [해제]`), 고정하는 동작은
조회 결과 쪽에 둔다 — 방금 본 사람을 고정하는 게 실제 흐름이다.

### 퍼센타일 배지 — **만들었다가 뺐다**

`상위 38.9%` 배지를 요약 카드에 붙였다가 제거했다. 코드는 남아 있고
(`lib/tekken/rating-percentile.ts`) `app/` 어디서도 import 하지 않는다.

**막힌 줄 알았다가 뚫은 과정이 남길 만하다.** 밖에 있는 티어 표는
`GOD 1 = 상위 10.74%` 처럼 **랭크 이름** 기준인데 우리가 가진 건 숫자(`myRank`)뿐이고,
wavu 는 이름을 어디에도 안 준다(플레이어 HTML 560KB·API 문서 둘 다 확인).
번호↔이름을 추측해 이으면 CLAUDE.md 가 스테이지에서 금지한 것과 같은 짓이 된다.

그러다 `/api/replays` 가 **전 세계 리플레이 피드**라는 걸 API 문서에서 찾았다
(요청 하나 = 700초치 ≈ 4,200경기). 창 14개를 하루에 흩어 뽑고 플레이어 단위로
중복을 제거해 **37,496명** 표본을 만들었다. 단 이름이 필요 없어진다 —
레이팅으로 직접 백분위를 낸다.

| | |
|---|---|
| 중앙 | 1,507 |
| 상위 25% | 1,705 |
| 상위 10% | 1,899 |
| 상위 1% | 2,228 |

**4-E 의 결론과 모순이 아니다.** 거기서 문제였던 건 *개인 지표(실력·지구력)를
남과 비교해 점수로 만든 것*이다 — 지표의 뜻이 인구에 의존할 이유가 없는데 의존했다.
`상위 몇 %` 는 **인구 비교가 곧 정의**라 모집단이 바뀌면 값이 바뀌는 게 정상이고,
표본 수·수집 시점·"활동 중인 플레이어 기준"을 감추지만 않으면 된다.
표본도 80명 대 37,496명이다.

다시 꺼낼 때: `npx tsx scripts/build-rating-baseline.ts <창수>` 로 기준값을 새로 뽑고
요약 카드에 배지를 붙이면 된다. **시즌이 바뀌면 반드시 다시 뽑아야 한다** —
레이팅 분포가 통째로 움직인다.
