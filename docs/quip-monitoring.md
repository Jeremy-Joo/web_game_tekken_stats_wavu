# 멘트 모니터링 — 무엇을, 어떻게 감시하는가

멘트(`app/jokes.ts`/`app/fact-jokes.ts`)는 사람이 직접 웹사이트를 써보기 전까지는
"이상한 조합"이 배포됐는지 알 방법이 없었다. 이 문서는 그걸 자동으로 잡는 두 시스템의
설계 결정과, 왜 그렇게 나눴는지를 적는다.

상태: **Part A 적용됨** (2026-08-07) · **Part B 설계 확정, 구현 전**

관련 문서: [joke-themes.md](joke-themes.md) · [advice-text.md](advice-text.md) ·
[mood-baseline.md](mood-baseline.md)

---

## 1. 배경 — 실제로 터진 두 계급의 사고

**사고 1 (2026-08-07, 구조적 불일치)**: 레이팅 1447(승률 44%)인 유저가 승단만 하고도
"프로 무대에 입성했습니다. 이제는 승격이 아니라 잔류를 고민해야 할 때입니다"를 받았다.
`app/fact-jokes.ts`의 `rankChange()` 풀에 있던 프로/리그 소재 문구에 레이팅 게이트가
없었던 게 원인 — `pickCoach()`가 이미 쓰던 `COACH_HIGH_MIN_RATING(1950)` 임계값을
재사용해 승단 풀 5줄·강등 풀 4줄(ko/en/ja)을 고레이팅 전용으로 게이트해 고쳤다.

**사고 2 (2026-08-06, 분포 편중)**: 승단·연승·오늘 몰림 멘트가 실측 이벤트의 68%를
차지해 마일스톤·최고갱신 같은 진짜 희귀 사건과 뒤섞였다. 확률 게이트(`RANKCHANGE_EVERY`
등)로 고쳤고, 연승·오늘 몰림은 사용자 요청으로 아예 뺐다.

두 사고는 성격이 다르다 — 사고 1은 "이 문구가 이 맥락에 나오면 안 된다"(내용과 상태의
불일치), 사고 2는 "이 문구가 너무 자주 나온다"(카테고리 간 노출 빈도 불균형). 하나의
검사로는 둘 다 못 잡는다고 보고 두 시스템으로 나눴다.

## 2. 설계 — 두 갈래로 나눈 이유

- **Part A (저장소 기반 구조 검사)** — 실제 플레이어 표본으로 멘트 파이프라인
  (`fetchReplays → normalizeReplays → sessionAdvice → buildQuipFacts → pickJoke/pickCoach`)
  을 재현하고, 사고 1과 같은 어휘가 자격 미달 레이팅에서 나오는지 키워드 규칙으로
  검사한다. GA 데이터가 필요 없다 — 코드가 배포되기 전에도 잡을 수 있다.
- **Part B (GA 실사용 분포 추적)** — 실제 트래픽에서 어떤 멘트 "풀"이 얼마나 자주
  나가는지 추적해 사고 2 같은 편중을 자동으로 감시한다. Part A의 합성 표본(수십 명)으로는
  실제 트래픽 규모의 분포 문제를 재현할 수 없다 — 이건 진짜 방문자 수가 필요하다.

## 3. 왜 개별 줄이 아니라 풀 단위인가

Part B를 설계할 때 "GA에 개별 멘트 줄 단위로 남길까, 풀(무드+사다리단계) 단위로 남길까"를
검토했다. **풀 단위로 정했다**, 이유:

1. 사고 1은 GA 데이터 없이 Part A(내용 대조)만으로 잡힌다 — 추적 단위 선택과 무관하다.
2. 지금까지 실제로 터진 분포 문제(사고 2, 그리고 그 이전의 rankChange/시각 사다리 굶주림)
   모두 "카테고리 단위" 문제였지 "한 풀 안의 특정 줄" 문제가 아니었다.
3. `app/jokes.ts`의 `pick()`이 `seed % pool.length`로 뽑는 구조상 풀 안에서는 이미
   고르게 분산되도록 설계돼 있어, 줄 단위 쏠림 자체가 구조적으로 드물다.
4. 개별 줄 단위로 가려면 지금 ~500줄(ko/en/ja, `app/jokes.ts`/`app/fact-jokes.ts`)에
   안정적 ID를 붙이는 1회성 대규모 마이그레이션과, 이후 계속되는 ID 관리 부담이 든다.
   그 비용을 정당화할 근거가 아직 없다.

**보류이지 기각이 아니다** — 풀 단위 데이터가 실제로 "이 풀 안을 더 들여다봐야겠다"는
구체적 증거를 주면 그때 개별 줄 단위로 올린다.

## 4. 키워드 목록과 그 한계

Part A(`scripts/check-quip-simulation.ts`)의 규칙은 `['프로', '리그', '감독', '코치',
'승격']` 다섯 단어를 `text.includes()`로 정확히 대조한다. 이건 **사고 1 계급을 겨눈 좁은
회귀 방지선**이지, "톤이 이상한 모든 문구"를 잡는 일반적인 안전망이 아니다. 새로운
"이 맥락에서만 나와야 하는" 소재를 추가할 때는 이 목록에 없는 어휘라면 이 검사가
보호해주지 않는다 — 게이트를 직접 코드로 챙겨야 한다.

## 5. 수동 단계 (Part B, 구현 시)

Part B를 배포하면 사용자가 직접 **GA4 → 관리 → 맞춤 정의 → 맞춤 측정기준**에서
`quip_pool`, `rating_bucket`(이벤트 범위) 두 개를 등록해야 한다 —
`app/admin/page.tsx`의 `ui_lang` 등록 안내와 같은 방식. 등록은 소급 적용되지 않는다 —
등록 전에 발생한 `quip_shown` 이벤트는 Data API로 영영 못 읽는다.
